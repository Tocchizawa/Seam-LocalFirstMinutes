# Live Notes v2 — ゴールデンサンプルと時系列評価ケース

> 目的: 「ノートの見た目と意味」が実際に進化しているかを評価するための参照例。
> 参考: ユーザー提示の23分程度のNRI共通部品とgRPCに関する会話。
> これは製品の固定テンプレートではない。また、ソースコードとの照合済みの技術仕様ではなく、**文字起こしで説明されたことの整理例**である。

## A. 発言列をどう解釈するか

会話の概念的なイベント:

| 時間帯 | 会話で起きたこと | ノートに必要な変化 |
|---|---|---|
| 02分頃 | `main.go`から共通部品を生成し、gRPC側に渡していると説明 | テーマ「NRI共通部品の受け渡し」を形成 |
| 03〜06分 | `NewGRPCServer` や `NewNriPoint` の役割を確認、同じ問いを繰り返す | 同じtopic内の確認中項目に集約。新見出しを乱立させない |
| 06〜12分 | `_`で受け取る引数の意味、引数なしのNRIハンドラー生成を確認 | 「共通部品はNRI側へ未接続」という結論に昇格し、未解決の問いを解消 |
| 13〜16分 | `server.NewServer`と`NewNriPoint`の呼出順・役割を確認 | 処理フローと部品の役割の説明を正す。繰り返しは統合 |
| 17〜19分 | 共通部品をハンドラーへ渡す変更の方向を説明 | 「接続方針」を追加/更新し、依存関係の図を完成させる |
| 19分以降 | 話題を区切り、次へ移る | 今までの内容を維持。以降新しいテーマがあれば新見出しへ |

注: 元発言には誤認識が多く、関数名や型の表記は会話の意図から仮統一した。実際のコードの正確なシンボル名は検証対象。

## B. 5分時点の文書例

```markdown
# NRI連携: 共通部品からgRPCへの流れ

## 1. 共通部品の生成と受け渡し

`main.go`の起動処理でNRI連携に必要な共通部品を作り、
gRPCサーバーを組み立てる処理へ渡している。

**確認中:** 渡した共通部品がNRIポイント受付部品でも使われているか。
```

この段階では、まだ「結論」を断定しない。相づち・関数の場所を尋ねる発言ごとに箇条書きを作らない。

## C. 12分時点の文書例

```markdown
# NRI連携: 共通部品からgRPCへの流れ

## まず押さえること

**共通部品は生成されるが、NRIハンドラーにはまだ接続されていない。**

## 1. 現状の受け渡し

1. `main.go`でNRI共通部品を生成する。
2. gRPCサーバーの組み立て関数へ渡す。
3. 受け取った引数は`_`として使用されていない。
4. `NewNriPoint`も引数なしで呼ばれる。

このため、NRIポイント受付部品から共通部品を使えない状態。

## 2. 接続方針

（議論待ち）
```

5分時点の「確認中」が**解消されている**こと。同じ問いをさらに「未解決」として残さない。もし本文に「議論待ち」の空見出しを表示したくなければ、セクション自体を未作成とする方がさらに自然。

## D. 18分時点の文書例

```markdown
# NRI連携: 共通部品からgRPCへの流れ

## まず押さえること

**共通部品はgRPCサーバーの組み立て処理へ渡されるが、NRIポイントの受付部品に渡っていない。**

## 1. 現在の処理の流れ

1. `main.go`で共通部品（NriDeps）を生成。
2. `NewGRPCServer`に渡す。
3. 引数は`_`として未使用。
4. `NewNriPoint()`は引数なしでNRI受付部品を生成。
5. 受付部品をgRPCサーバー側へ登録する。

## 2. 関数の役割

- **NriDeps:** NRIとの通信に必要な共通部品。
- **NewGRPCServer:** gRPCサーバーの組み立て処理。
- **NewNriPoint:** NRIポイント用受付部品の生成。
- **grpcserver.NewServer:** gRPCサーバー本体の構築。

## 3. 接続する場合の変更方針

`NewGRPCServer`でNriDepsを保持し、`NewNriPoint`へ引数で渡す。
`NewNriPoint`側で依存部品を受け取るよう変更する。

※ハンドラーの具体的な実装・接続完了は今後確認する。
```

ここでは新しいセクションを追加しているが、各発言ごとに独立した「論点」行を作っていない。主題・原因・役割・方針の4つに再編されている。

## E. 会議終了時の理想例

```markdown
# NRI共通部品とgRPCハンドラーの接続

## 結論

**NRI共通部品は起動時に生成され、gRPCサーバーの組み立て処理までは渡されるが、NRIポイント受付ハンドラーではまだ利用されていない。**

## 現在の処理フロー

1. `main.go`の起動処理でNRI共通部品を生成する。
2. `NewGRPCServer`へ共通部品を引数として渡す。
3. gRPCサーバーの組み立て処理では、その引数を`_`で受けており利用していない。
4. NRIポイント受付部品を作る`NewNriPoint()`も引数なしで呼ばれている。
5. 生成された受付部品がgRPCサーバーへ登録される。

→ **共通部品の生成とNRIハンドラーの受付機能は、現状では依存関係が接続されていない。**

## 各部品の役割

| 部品 | 役割 |
|---|---|
| NriDeps | NRI連携に必要な共通部品をまとめた依存情報 |
| NewGRPCServer | 受付ハンドラーを含むgRPCサーバー構成を組み立てる |
| NewNriPoint | NRIポイント用のgRPC受付ハンドラーを生成する |
| grpcserver.NewServer | 実際のgRPCサーバー本体を構成する |

## 接続のために必要な変更

1. `NewGRPCServer`で受け取る共通部品を使える形にする。
2. `NewNriPoint`に共通部品を引数で渡す。
3. `NewNriPoint`側でそれを受け取り保持する。
4. NRIの業務処理をハンドラーへ接続する。

## 確認事項

- 正確な関数名・型・ファイル位置はソースコードで要確認。
- 基盤構築と業務処理実装の対応範囲を確認する。
```

**この形を丸暗記したテンプレートにはしないこと。** 別の会議を処理した際には、その議論の構造を反映した異なる見出しを使う。

## F. 失敗例と合格例

| イベント | 失敗例 | 合格例 |
|---|---|---|
| 「どうつながる？」と3回確認 | 「未解決: ...」が3行 | 既存の問い1件へ関連発言を集約 |
| 「引数`_`は使っていない」と確認 | 質問を残して「論点:使っていない」を追加 | 問いはanswered、本文に原因を反映 |
| `NewNriPoint`の役割が確定 | 「論点」「未解決」をさらに2行 | 「各部品の役割」の1行を修正 |
| 実装方法の話へ進む | 項目が時系列末尾にばらばらに追加 | 同テーマの「接続方針」を作る |
| 以前の話題に戻る | 「NRIデプスの話（2）」を追加 | 既存のNRI共通部品topicを更新 |
| 人間が「NriDeps」に修正 | 数十秒後に「nri lips」に戻る | 手動表記を尊重し続ける |
| 不明瞭な関数名をASRが出力 | 根拠なしに正規コード名を断定 | 不確実とし、用語集/ユーザー編集で補正 |

## G. その他の会議への汎化テスト

### 比較検討の会議

入力例: 「A案は初期費用が低い」「B案は運用コストが低い」「結局B案で進めよう」「ただ法務確認が必要」。

合格例の骨格: 背景／評価軸／A案とB案の比較／判断と根拠／法務確認。**仕様検討まで技術フローの見出しをコピーしない**。

### 障害調査の会議

入力例: 「APIがタイムアウト」「DBが高負荷かも」「確認したらDBではなく外部依存先の遅延」「対処としてリトライを調整」。

合格例の骨格: 症状／調査で判明した原因／除外された仮説／対処方針／残課題。除外された仮説を「現在の原因」に残さない。

### 仕様策定の会議

入力例: 「エラー時に注文失敗にする？」「決済前なら全額返却」「決済後なら注文成功で後続救済」。

合格例の骨格: 前提／ケース別の振る舞い／例外処理／未確認事項。**条件ごとの振る舞い**を崩さず整理する。

## H. 評価の運用

- 各時間スナップショットを保存して比較する。
- ルーブリック: 構造・重複の少なさ・状態の正確さ・根拠の忠実性・可読性・時間的一貫性（各0〜5）。
- 早い段階で結論を勝手に断定していないか確認する。
- 後半の回答で前半の問いが解消されたか確認する。
- 話が増えても過去情報が消えないことを確認する。
- 補足・反対意見・条件分岐を省略して簡潔にしすぎていないか確認する。
